  # 实时双线程骨架说明

> 对应代码：`violin_midi_json/src/violin_midi_json/streaming.py`
>
> 目的：为后续视觉识谱（OMR）接入预留稳定接缝，先定义线程边界和数据契约，不改现有离线转换主链路。

---

## 1. 背景与目标

老师建议的思路是经典生产者-消费者模型：

- 线程 A：读取一小节音符并完成处理；
- 线程 B：读取动作并执行。

本项目骨架采用这一思路，但强调一个关键边界：

- 线程切分点放在“决策之后、执行之前”；
- 队列里放的是“已完成运弓决策的动作”，不是原始音符。

这样可以保证：

- 生产侧只关心音乐和决策；
- 消费侧只关心执行（编码、发 ROS、发串口等）；
- 后续替换数据源或执行端时互不影响。

> **重要补充（本次补齐）**：早期骨架只把“弓向决策”放进了实时管线，却把“指法决策”
> 留在了实时管线之外——因为指法原本由 `GlobalFingeringPlanner` 整曲一次算完，而实时读谱
> 只有按小节增量到达的音符。本次新增了 `OnlineFingeringPlanner`（窗口化在线指法规划），
> 把指法决策也变成了一条可替换的实时接缝，见第 2.2 节。

## 2. 骨架包含哪些对象

### 2.1 `ViolinAction`

线程间传递的最小动作单元（不可变）：

- `note: ConvertedNote`
- `decision: BowDecision`

含义：

- `note` 保留音符和指法信息；
- `decision` 保留弓向、连奏、弓速等决策结果。

### 2.2 `NoteSource`（输入接口）

音符来源抽象，要求按小节产出【原始】`MidiNote` 批次（尚未定指法）：

- `iter_measures() -> Iterable[Sequence[MidiNote]]`

可替换实现：

- 现在：`MidiMeasureSource`（离线，把 MIDI 文件按小节切片）；
- 未来：`VisionScoreSource`（视觉识谱实时输入，当前为占位实现，见第 6 节）。

### 2.3 `FingeringPlanner`（指法接口，本次新增）

指法决策抽象，按批次喂入原始音符、返回已定指法的音符：

- `feed(notes: Sequence[MidiNote]) -> list[FingeredNote]`
- `flush() -> list[FingeredNote]`

- `FingeredNote` = `note`（原始音符）+ `fingering`（选定的 `FingeringCandidate`）。

可替换实现：

- 现在：`OnlineFingeringPlanner`（窗口化在线规划，见第 4 节）；
- 未来：可替换为任何满足 `feed`/`flush` 契约的实现（例如更高级的在线算法）。

### 2.4 `ActionSink`（输出接口）

动作去向抽象：

- `put(action: ViolinAction) -> None`
- `close() -> None`

可替换实现：

- 现在：写文件或 `ListActionSink`（内存收集，供测试/调试）；
- 未来：ROS 发布、串口发送、硬件执行。

### 2.5 `RealtimePipeline`（双线程骨架）

负责拉起两个线程和中间有界队列：

- 生产者 `_produce()`：
  - 按小节读【原始】音符；
  - 调 `fingering.feed(...)` 增量定指法 → `build_converted_note(...)` 组装；
  - 入弓向前瞻缓冲 → 调 `engine.decide_streaming(...)` 增量定弓向；
  - 逐个动作 `queue.put(...)`。
- 消费者 `_consume()`：
  - `queue.get()` 拉取动作；
  - 调用 `sink.put(action)` 执行。

提供：

- `start()`：启动线程；
- `join()`：等待线程结束。

## 3. 线程安全与状态归属

这部分是骨架最重要的约束。

### 3.1 唯一共享状态

只有 `queue` 是线程间共享对象。

### 3.2 决策器状态归属

`BowDecisionEngine` 和 `OnlineFingeringPlanner` 都是有状态对象，必须由生产者线程独占。
消费者线程不得读取或修改任何决策器内部状态。

### 3.3 不可变动作对象

队列中传递 `ViolinAction`（冻结 dataclass），防止消费侧误改数据，减少并发错误。

---

## 4. 窗口化在线指法规划（本次新增）

`OnlineFingeringPlanner` 解决“全局指法 DP 需要整曲、实时读谱只有增量”的矛盾：

1. 维护一个滑动窗口缓冲区，攒满 `window_size` 个音符；
2. 用 `GlobalFingeringPlanner.plan(window, initial=上一个已提交指法)` 求窗口内最优指法；
3. 只提交前 `commit_size = window_size - lookahead_size` 个音符（它们仍有足够未来上下文，决策稳定）；
4. 窗口前滑，边界处用上一个已提交指法做 DP 初值，保证跨批次连续；
5. 流结束时 `flush()` 提交缓冲区剩余音符。

参数语义：

| 参数 | 含义 |
|------|------|
| `window_size` | 一次 DP 处理的音符数（越大越接近全局最优，但实时延迟越大） |
| `lookahead_size` | 提交前保留的未来上下文音符数（0 ≤ lookahead < window） |

> 关键点：`GlobalFingeringPlanner.plan()` 新增可选 `initial` 参数，把“上一个已确定指法”
> 作为 DP 第 0 步的初值，从而让分段结果在边界处与整曲结果一致。

---

## 5. 有界队列的意义

骨架默认使用 `Queue(maxsize=64)`（可配置）。

意义：

- 当消费端变慢时，生产者会阻塞；
- 阻止无界积压导致延迟不断变大；
- 能更早暴露“执行跟不上”这一实时系统关键问题。

---

## 6. 当前范围与非目标

当前骨架是“结构就位”，不是“实时功能已完成”。

已完成：

- 线程边界和数据契约；
- 双线程运行框架；
- 结束哨兵机制（生产结束后通知消费者退出）；
- **指法实时接缝**：`FingeringPlanner` + `OnlineFingeringPlanner`（窗口化在线规划）；
- **增量弓向**：`BowDecisionEngine.decide_streaming()`（状态跨调用保持，不批量重置）。

尚未实现（依赖硬件/后续阶段）：

- 真实视觉识谱输入（`VisionScoreSource` 仍是占位）；
- 墙钟同步调度（按绝对时间发布动作）；
- ROS/Arduino 实时发送策略（`RobotRealtimeSink` 未实现）；
- 异常恢复与重试策略。

## 7. 未来接入步骤（建议顺序）

1. 实现 `VisionScoreSource`：把 OMR 输出组织成按小节 `MidiNote` 批次，替换当前的占位实现；
2. 实现 `RobotRealtimeSink`：将 `ViolinAction` 编码并按时序发送到 ROS/Arduino；
3. 在集成层组装并启动：

   ```python
   source = VisionScoreSource(...)                          # 或离线 MidiMeasureSource
   fingering = OnlineFingeringPlanner(window_size=8, lookahead_size=4)
   engine = BowDecisionEngine(BowDecisionOptions(tempo_bpm=source.tempo))
   sink = RobotRealtimeSink(...)
   pipeline = RealtimePipeline(source, fingering, engine, sink)
   pipeline.start()
   pipeline.join()
   ```

4. 加入监控指标：队列长度、生产/消费速率、丢包与超时统计。

---

## 8. 与现有离线流程关系

离线流程保持不变：

- `converter.py` 继续负责 MIDI 到 JSON/BIN 的批处理转换。

实时骨架是增量扩展：

- 新增模块/类，不破坏当前 CLI 和离线输出；
- `build_converted_note()` 与 `BowDecisionEngine`、`GlobalFingeringPlanner` 在离线和实时场景复用。
